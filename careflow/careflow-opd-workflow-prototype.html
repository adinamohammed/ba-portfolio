📐 Business Rules
▸ Patient search must happen before creating a new record.
▸ Follow-up visits must be linked to an existing Patient ID.
▸ Token is department and session specific.
▸ Mandatory fields: Name, Age, Gender, Mobile, Department, Session, and Doctor.
▸ Duplicate mobile triggers existing patient suggestion.
▸ Consultation Fee Status is tracked at MVP level; full billing is outside scope.
▸ Token printing/reprinting is manual in MVP.
▸ Digital Health ID / PHR: Future scope only.

📖 Demo Guide

Prototype explanation for recruiters and interviewers.

📌 Project Snapshot

Project:CareFlow Smart OPD & Digital Patient Records System
Prototype:CareFlow OPD Workflow Prototype
Type:Independent BA Portfolio Case Study
Domain:Healthcare / OPD Coordination
Prepared by:Adina Mohammed
Purpose:Visual BA communication artefact

✅ What This Demo Is

  • Front-end OPD workflow prototype
  • BA communication and portfolio artefact
  • Visual representation of registration, routing, consultation, lab/pharmacy, and reporting
  • Fictional demonstration using only made-up patient data
  • Tool to explain workflows, fields, and business rules to interviewers

❌ What This Demo Is Not

  • Not a production HMIS/EMR
  • Not copied from any live hospital system
  • Not connected to ABHA/PHR, payment gateway, WhatsApp/SMS, lab machines, pharmacy inventory, or real database
  • Not using real patient data
  • Not covering IPD, ICU, OT, surgery, or inpatient billing
  • Not a full hospital ERP

🔍 Research & Observation Note

  • Prototype is informed by common publicly documented OPD/HMIS patterns and high-level OPD workflow observation; it is a fictional BA portfolio prototype, not a live HMIS clone.
  • No real hospital screenshots, patient records, doctor names, URLs, or proprietary screens are used.
  • The doctor queue/search section reflects a common pattern: doctors open a patient from an assigned queue before consultation.

🚶 Suggested Walkthrough

  1. Go to OP Registration → search mobile 9876543210 → see duplicate patient suggestion
  2. Fill the registration form → click Register Visit → see generated token
  3. Go to Token Queue → view department queue and active token board
  4. Use Routing Action Panel → select token → update status
  5. Go to Doctor Workspace → search/open patient from Doctor Patient Queue → review patient header and allergy flag
  6. Add a lab order and a prescription item → Finalise Prescription
  7. Go to Lab & Pharmacy → upload an external report → mark a medicine dispensed
  8. Go to Admin Dashboard → select report focus → export demo report

🖥 Screens Covered

  • OP Registration — patient search, form, token generation
  • Token Queue — department queue, active board, routing
  • Doctor Consultation — patient queue/search, vitals, notes, lab orders, e-prescription, follow-up, history
  • Lab & Pharmacy — order tracking, report upload, dispensing
  • Admin Dashboard — KPIs, department load, SQL reporting map

🎯 BA Skills Demonstrated

  • OPD process and stakeholder role understanding
  • Field-level data capture and validation rules
  • Business rule translation into UI behaviour
  • MVP boundary and scope control
  • UAT scenario thinking across all modules
  • SQL-based reporting logic design
  • Privacy and role-based access awareness
  • Stakeholder communication through visual artefact

🔗 How It Connects to BA Artefacts

  • Process flows — explain the patient journey across screens
  • Data dictionary — each field has a label, type, and validation rule
  • Business rules — shown on every screen as a dedicated panel
  • UAT scenarios — each interactive action maps to a testable scenario
  • SQL reporting notes — Admin Dashboard SQL mapping table
  • Stakeholder analysis — each screen shows primary user role

💬 Interview Talking Points

  • I created this prototype to make BA requirements visual and easy to discuss
  • I kept scope deliberately limited to OPD — not full hospital ERP
  • I excluded AI diagnosis and prescription for safety and scope control
  • I treated ABHA/PHR integration as future scope, not MVP
  • I used SQL mapping to show how operational questions can be answered from data
  • I designed each screen around a specific stakeholder role and their core tasks
  • In a real project, I would validate all screens with registration staff, doctors, lab, pharmacy, and admin
  • The business rules shown represent what I would document in a BRD/FRD
